# Stack Research

**Domain:** tModLoader world-generation APIs for retrofitting 8 existing flat-platform boss-arena `Subworld`/`GenPass` pairs with biome-themed decoration, multi-tier platforms, fall/trap containment, torch lighting, and a return-portal tile
**Researched:** 2026-08-15
**Confidence:** MEDIUM-HIGH (core `WorldGen`/`ModTile`/`TileID`/`TorchID` APIs verified against official tModLoader docs; StructureHelper API verified against its own wiki but NOT verified against the actually-installed local copy; no Context7 tModLoader library was available this session — all verification went through `docs.tmodloader.net` and `github.com/tModLoader/tModLoader`, both HIGH-confidence official sources)

This is an **additive** research pass — it assumes the existing v1.0 architecture (`Subworld` subclass + single `GenPass` per arena, raw `Main.tile[x,y]` array writes for the flat platform body, `[JITWhenModsEnabled]`-guarded modded-tile passes for Astral/Briar) is correct and validated. Nothing below proposes replacing that; it proposes what to *add* to each existing `ApplyPass` (or a new shared pass appended after it).

## Recommended Stack

### Core Technologies

No new core technologies. All five v1.1 features are achievable with tModLoader 1.4.4.9's existing `Terraria.WorldGen` / `Terraria.WorldBuilding.GenPass` / `Terraria.ModLoader.ModTile` surface — the same surface already in use for the 8 existing `*PlatformPass` classes. No new `modReferences`/`weakReferences` line is required in `build.txt` for the core ask.

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| `Terraria.WorldGen` static class (`WorldGen.PlaceTile`, `PlaceObject`, `PlaceWall`) | Ships with tModLoader 1.4.4.9 (no separate version) | Frame-aware, anchor-validated placement of individual tiles/walls/multitile objects during a `GenPass` | This is the layer the existing platform passes deliberately bypass (they raw-write `Main.tile[x,y]` for speed on a 10000-wide bulk fill). Every NEW feature in this milestone places *sparse, frame-important* content (torches, platforms, a portal tile) where raw writes leave `FrameX`/`FrameY` at 0 and render wrong — `WorldGen.PlaceTile`/`PlaceObject` compute correct framing and honor anchor rules automatically. Verified signature: `PlaceTile(int i, int j, int type, bool mute=false, bool forced=false, int plr=-1, int style=0)`; `PlaceObject(int x, int y, int type, bool mute=false, int style=0, int alternate=0, int random=-1, int direction=-1)`. [docs.tmodloader.net WorldGen](https://docs.tmodloader.net/docs/preview/class_world_gen.html) — HIGH confidence |
| `Terraria.ID.TorchID` + `TileID.Torches` | Ships with tModLoader 1.4.4.9 | Biome-styled torch placement for feature (4) | One vanilla tile ID (`TileID.Torches`), many styles selected via `WorldGen.PlaceTile`'s `style` param and the `TorchID` constants: `Torch, Demon, Corrupt, Crimson, Hallowed, Jungle, Ice, Desert, Coral, Cursed, Ichor, Bone, ...` (verified member list). This maps 1:1 onto 6 of the 8 existing arenas (Corruption→`TorchID.Corrupt`, Hallow→`TorchID.Hallowed`, Underworld→`TorchID.Demon` or `Ichor`, Jungle→`TorchID.Jungle`, Desert→`TorchID.Desert`, plain→`TorchID.Torch`) with zero new dependency. [docs.tmodloader.net TorchID members](https://docs.tmodloader.net/docs/1.4-stable/class_terraria_1_1_i_d_1_1_torch_i_d-members.html) — HIGH confidence |
| `Terraria.ModLoader.ModTile` (custom `PreDraw` override) | Ships with tModLoader 1.4.4.9 | Invisible solid boundary tile for feature (3) | Vanilla has no built-in "invisible solid" tile ID. The verified, standard tModLoader idiom is a custom `ModTile` with `Main.tileSolid[Type] = true` (blocks movement) and `public override bool PreDraw(...) => false` (skips the game's default tile draw entirely, and since the override draws nothing else, the tile is invisible). This is a documented `ModTile` hook, not a hack. [docs.tmodloader.net ModTile](https://docs.tmodloader.net/docs/preview/class_mod_block_type.html) — MEDIUM-HIGH confidence (hook behavior confirmed via official docs; the "make it fully invisible" composition is a standard community pattern, not literally spelled out as a worked example on tModLoader's own docs page) |

### Supporting Libraries / APIs (no new build.txt entries)

| API / Pattern | Purpose | When to Use |
|---------------|---------|-------------|
| `Terraria.ID.WallID` + `WorldGen.PlaceWall(int i, int j, int type, bool mute=false)` | Biome-themed background walls for feature (1) | Purely cosmetic layer behind the platform (e.g. `WallID.JungleUnsafe` for Jungle, `WallID.Pearlstone` for Hallow, `WallID.HellstoneBrick`/Ash-brick for Underworld, `WallID.Sandstone` for Desert). **Confirm before use:** none of this project's existing `*PlatformPass` classes place any wall at all today, and Phase 9/10 already validated all 7 biome flags with zero walls present — so walls are additive decoration only, never load-bearing for a Zone/Biome flag check (the existing class-header comments already document this per-biome: flag checks read `SceneMetrics`/tile-count, not wall presence). |
| `Tile.LiquidAmount` / `Tile.LiquidType` (`Terraria.ID.LiquidID`: `Water`, `Lava`, `Honey`, `Shimmer`) | Thematic liquid pools (e.g. lava moat in the Underworld arena, water pool in Jungle) | Same raw-tile-array-write pattern already used for the platform body itself (`tile.LiquidAmount = 255; tile.LiquidType = LiquidID.Lava;`) — no new API family, just a different `Tile` field. LOW priority for this milestone (not explicitly requested), MEDIUM confidence on exact settle behavior inside a custom `GenPass` list (vanilla's own generation normally runs a dedicated "Settle Liquids" pass after all custom tasks; whether SubworldLibrary's task pipeline also settles liquids placed by a custom pass was not directly verified this session — treat any liquid pass as needing live in-game verification for visual "sloshing" correctness, not just placement). |
| `Terraria.ModLoader.ModTile.RightClick(int i, int j)` returning `bool` | Return-portal tile for feature (5) | **Already validated in this codebase** — `Tiles/Test1Tile.cs` is the exact reference pattern (right-click claims the interaction, returns `true`, calls into a `Systems/` static method). For the return trip, the equivalent call is `SubworldSystem.Exit()` (already used elsewhere in the codebase per `01-RESEARCH.md`/debug docs) instead of `BossArenaRoutingRegistry.Enter(...)`. No new tModLoader API — same `ModTile` + `TileObjectData.Style1x1` shape as `Test1Tile`. |
| `Terraria.ModLoader.ModPlayer.PostUpdate()` | Defense-in-depth Y-clamp for feature (3) | Verified hook ordering: `PreUpdate()` → `PreUpdateMovement()` → [position/velocity applied] → `PostUpdateMiscEffects()` → `PostUpdateRunSpeeds()` → `PostUpdate()` (runs "at the very end of `Player.Update`"). `PostUpdate()` is the correct place to hard-clamp `player.position.Y` (and zero `player.velocity.Y`) as a *backstop* if a boss's attack or knockback ever launches the player faster than solid boundary tiles can stop them in one tick — solid tiles remain the primary containment mechanism (see below), this is a belt-and-suspenders addition, not a replacement. Gate it with the existing `BossArenaRoutingRegistry.IsAnyArenaActive()` check so it never fires in the main world. [docs.tmodloader.net ModPlayer](https://docs.tmodloader.net/docs/stable/class_mod_player.html) — HIGH confidence on hook order/timing; the "use it for a Y-clamp" application is this research's own recommendation, not a documented worked example. |
| `Terraria.Player.Teleport(Vector2 newPos, int Style=0, int extraInfo=0)` | NOT needed for feature (5) as scoped | Verified signature exists (repositions a player within the *same* world, used by vanilla Teleporter tiles/Magic Mirror). Cross-world return in this project is a subworld transition, which is `SubworldSystem.Exit()` territory (SubworldLibrary), not `Player.Teleport` (single-world repositioning) — noted here specifically so a future implementer doesn't reach for the wrong API. Would become relevant only if a later milestone adds an in-arena "teleport between platform tiers" convenience, not for entry/exit. |

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|--------------------------|
| Hand-rolled loop calls to `WorldGen.PlaceTile`/`PlaceObject`/`PlaceWall` for multi-tier platforms (feature 2), directly in each biome's `*PlatformPass.ApplyPass` (or a new shared helper pass run after it) | [StructureHelper](https://github.com/ScalarVector1/StructureHelper) (`Generator.GenerateStructure(string path, Point16 pos, Mod mod, bool fullPath=false, bool ignoreNull=false, GenFlags flags=GenFlags.None)`, verified signature) — author each arena's multi-tier layout visually in-game, export to a `.struct` file, stamp it in with one call | Only if a future milestone wants hand-authored, visually complex, non-parametric structures (e.g. an ornate stone amphitheater) that would be painful to describe as nested `for` loops. For THIS milestone's ask — a handful of simple rectangular platform tiers at different Y-offsets, sized per-biome — plain loops are simpler, add zero new external mod dependency (StructureHelper is a real Steam Workshop mod the player would need installed and enabled, on top of the 6 already-weak-referenced mods), and stay consistent with the 100%-hand-rolled convention every existing `*PlatformPass` already uses. Revisit if platform geometry complexity grows significantly. |
| Custom `ModTile` with `PreDraw() => false` for invisible boundary tiles | Reuse a real, thematically-matching solid tile (e.g. more of the same biome stone) as the boundary, just placed further from the platform surface | Visible-but-thematic boundary is actually simpler (zero new `ModTile` class, same raw-array-write convention as the platform body) and may look MORE correct for a "cave ceiling/floor" framing than true invisibility, which can look like the player is floating against a hard edge. Recommend defaulting to thematic-solid unless playtesting shows the visible boundary feels too enclosing; keep the invisible-`ModTile` option in reserve since it's a known, low-effort pattern if needed. |
| Solid boundary **tiles** (raw `Main.tile[x,y]` writes, same convention as the platform body) as the primary anti-fall mechanism | `ModPlayer.PostUpdate()` runtime Y-clamp as the ONLY mechanism (no tiles) | Runtime-only clamping is fragile against anything that bypasses normal Y-velocity integration (teleport-style boss attacks, certain dashes) and gives zero visual/spatial cue to the player about where the boundary is. Tiles are the primary, visible, always-correct containment; the `ModPlayer` clamp (see Supporting Libraries above) should be additive, not a replacement. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Raw `Main.tile[x,y]` array writes (the pattern all 8 existing `*PlatformPass` classes use for the platform body) for torches, platforms, multi-tile objects (teleporter/portal tile), or anything else with `Main.tileFrameImportant[type] == true` | Raw writes leave `Tile.FrameX`/`Tile.FrameY` at 0. For a bulk solid fill of a single self-merging tile type (Stone, Pearlstone, etc.) this looks fine because neighbor-merge framing is visually forgiving at scale; for `TileID.Torches` (whose FrameX literally selects WHICH torch-style sprite is drawn) or `TileID.Platforms` (whose frame determines one-way-passable orientation) an unframed raw write will render the wrong sprite or behave like a solid block instead of a platform. This is exactly the class of bug the project's own `09-RESEARCH.md`/`STATE.md` Desert stack-overflow incident (falling-Sand + unframed neighbors recursing through `WorldGen.SquareTileFrame`) already brushed up against once. | `WorldGen.PlaceTile(i, j, type, style: ...)` / `WorldGen.PlaceObject(...)` for every frame-important addition in this milestone. Keep raw writes ONLY for the existing bulk solid-body fills (unchanged). |
| Adding StructureHelper as a new `weakReferences` dependency just to place 2-4 rectangular platform tiers per arena | New external Steam Workshop mod dependency (the player must have it installed+enabled) for a task plain loops already solve in a few lines; also would need its own `[JITWhenModsEnabled("StructureHelper")]` isolation layer added to every arena, mirroring the Astral/Briar discipline, for a net decrease in simplicity | Hand-rolled `WorldGen.PlaceTile`/raw-fill loops, per Alternatives Considered above |
| `Player.Teleport(...)` for the arena return trip (feature 5) | Repositions the player WITHIN the current world/subworld only — does not cross the subworld boundary back to the main world at all, so it cannot satisfy "convenient return/re-entry" as scoped | `SubworldSystem.Exit()` (SubworldLibrary), called from a `ModTile.RightClick` override on a new return-portal tile, exactly mirroring `Tiles/Test1Tile.cs`'s existing entry-tile pattern |
| Assuming vanilla's `TileID.Torches` needs a custom `ModTile`/`ModifyLight` override to self-illuminate | Vanilla torches (any `TorchID` style) already self-illuminate out of the box via vanilla's own lighting code — `ModifyLight` overrides are only needed when authoring a brand-new MODDED light-emitting tile (e.g. `ExampleMod`'s `ExampleTorch`, which exists specifically to demonstrate that hook for custom content), not when placing a vanilla torch | `WorldGen.PlaceTile(i, j, TileID.Torches, style: TorchID.X)` — no custom `ModTile` class needed at all for feature (4) |

## Stack Patterns by Variant

**If the arena's biome-flag mechanism is vanilla `SceneMetrics` tile-weighting (Corruption/Hallow/Jungle/Desert) or height-only (Space/Underworld):**
- Add decorative/lighting/structural calls directly inside that biome's existing `*PlatformPass.ApplyPass`, using vanilla `TileID`/`WallID`/`TorchID` constants freely (no `[JITWhenModsEnabled]` needed) — matches the existing no-guard convention in `FlatStonePlatformPass`/`HallowPlatformPass`/`JunglePlatformPass`/`DesertPlatformPass`/`SpacePlatformPass`/`UnderworldPlatformPass`.

**If the arena's biome-flag mechanism is a modded `ModBiome.IsBiomeActive` tile-count hook (Astral/Briar):**
- Any NEW decorative/lighting/structural tile type that is itself a MODDED tile (e.g. a Calamity or Spirit torch/decoration tile, if one is chosen for closer theming) must be isolated the same way `AstralPlatformPass`/`BriarPlatformPass` already isolate `AstralStone`/`BriarGrass` — references live only inside the `using` directives and method body of an `ApplyPass` (or a new sibling method) tagged `[JITWhenModsEnabled("CalamityMod")]`/`[JITWhenModsEnabled("SpiritMod")]` respectively.
- Prefer VANILLA `TileID.Torches`/`WallID`/boundary tiles for these two arenas' new decoration where a close-enough vanilla equivalent exists (e.g. `TorchID.Ichor` or `TorchID.Cursed` as an Astral-adjacent stand-in) — this avoids adding a second layer of JIT-guarding on top of the existing one and keeps the "safe when the mod is disabled" property trivially true for anything new.
- If a genuinely modded decorative tile IS used, remember the project's own hard-won lesson (D-01/Pitfall 4, live-confirmed 2026-08-14): being reachable only from inside a `Tasks` list is NOT sufficient — the method itself must carry `[JITWhenModsEnabled(...)]`, because tModLoader's `AssemblyManager.JITAssembliesAsync` prefilters every method in the assembly regardless of call-reachability.

**If placing the new return-portal tile (feature 5) at a fixed, deterministic in-arena location (near spawn) rather than player-placed:**
- Call `WorldGen.PlaceTile(x, y, ModContent.TileType<ReturnPortalTile>(), forced: true)` from within the biome's `ApplyPass` (after the platform body is filled), at a position computed relative to that pass's own `surfaceY`/`Main.spawnTileX` values — do NOT hardcode a world-absolute coordinate, since each arena's `surfaceY` differs (e.g. `Main.maxTilesY/2` for most, `50` for Space, `650` for Underworld, `150` for Briar).
