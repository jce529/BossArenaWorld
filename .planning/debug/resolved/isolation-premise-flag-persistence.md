## Resolution

root_cause: |
  CONFIRMED, precise mechanism (source-verified against SubworldLibrary's own SubworldSystem.cs, matching installed v2.2.3.2 per 01-RESEARCH.md, and matching all empirical evidence including the user's own live re-checks):

  SubworldLibrary v2.2.3.2 has a BY-DESIGN feature, not a bug: two private helpers, `CopyDowned()` and `ReadCopiedDowned()`, unconditionally and bidirectionally sync a hardcoded whitelist of ~30 VANILLA `NPC`/`DD2Event` "downed" boolean static fields (including `NPC.downedSlimeKing`, `downedBoss1/2/3`, `downedMechBoss1/2/3/Any`, `downedPlantBoss`, `downedGolemBoss`, `downedMoonlord`, all four Lunar Tower flags, `downedQueenBee`, `downedDeerclops`, `downedQueenSlime`, `downedFishron`, `downedEmpressOfLight`, `downedAncientCultist`, and several vanilla event flags) between the main world and ANY subworld, on every single entry AND exit, regardless of `ShouldSave`/`NoPlayerSaving` and regardless of any carrier-item mechanism.

  Exact flow for our King Slime test: `SubworldSystem.Exit()` -> `ExitWorldCallBack()` calls `CopyMainWorldData()` while still "in" the subworld -> `CopyDowned()` captures the live (just-set-true) `NPC.downedSlimeKing` into `copiedData["downedSlimeKing"]`. Later in the same callback, `LoadWorld()` -> `LoadWorldFile()` loads the REAL main-world `.wld` file from disk (correctly reading `NPC.downedSlimeKing = false`, since the main file itself was never touched) -> but immediately afterward, the same method calls `ReadCopiedMainWorldData()` -> `ReadCopiedDowned()`, which unconditionally overwrites the freshly-loaded-correct `false` back to `true` from `copiedData`. No file corruption occurs (confirmed by the user: test-world terrain was NOT altered) -- this is a narrow, targeted, intentional flag-level sync, not a filesystem-level accident.

  This means the main world's actual .wld file itself is not touched by the round-trip in the way originally feared; however, if any LATER natural save event occurs (autosave, sleeping, normal exit-to-menu) while the in-memory `NPC.downedSlimeKing` is still (incorrectly, per this project's premise) `true`, that save WOULD persist `true` to the real main .wld file for real, explaining why the flag remains `true` even after later reloads.

  This DIRECTLY CONTRADICTS the specific claim in PITFALLS.md's Pitfall 1 and 01-RESEARCH.md's Pitfall 3 that SubworldLibrary's world-data-copy mechanism ("`CopyMainWorldData()`") only flows one-directionally (main -> subworld) and would not include vanilla downed-boss flags -- neither prior research doc appears to have read `CopyDowned()`/`ReadCopiedDowned()` directly (they are undocumented in SubworldLibrary's public XML doc comments and easy to miss without a full source read).

  Scope boundary confirmed important for Phase 2/3 planning: this whitelist is HARDCODED to vanilla fields only. It excludes: (1) any modded boss/event flags (Calamity `DownedBossSystem`, Spirit `MyWorld`, etc. -- these remain genuinely isolated, exactly as PITFALLS.md predicted for the modded case), (2) `Main.hardMode` on the return trip specifically (that key is "!"-prefixed in `CopyMainWorldData()`, and confirmed via source that "!"-prefixed reads are gated `if (current != null)` in `ReadCopiedMainWorldData()` -- i.e. applied only when ENTERING a subworld, never restored on exit), and (3) any WorldGen/tile-level side effects (ore conversion, structure placement, etc.), since those operate on `Main.tile[,]`, which is never part of `copiedData` at all. Predicted (not yet empirically verified) implication for the user's next question: killing Wall of Flesh in a subworld would auto-sync `NPC.downedBoss3 = true` back to the main world via this same mechanism, but `Main.hardMode` would stay `false` in the main world and the actual hardmode ore-conversion WorldGen call would never touch the main world's real terrain (it would only affect the subworld's own throwaway tiles, discarded on next entry since ShouldSave=false).
fix: |
  Defensive fix implemented in `Subworlds/BossArenaSubworld.cs`: overrode `Subworld.OnEnter()` to snapshot the main world's true pre-visit values of the exact same ~34-field vanilla `NPC`/`DD2Event` "downed"/event-flag whitelist that SubworldLibrary's own `CopyDowned()` uses, into private instance fields on the `BossArenaSubworld` singleton. Overrode `Subworld.OnExit()` to force-restore every one of those fields back to the snapshotted values.
  This works because of the confirmed call order in `ExitWorldCallBack()`: `cache.OnExit()` fires BEFORE `CopyMainWorldData()` captures the current flag values into `copiedData`. By restoring the correct pre-visit values in `OnExit()` first, whatever `CopyMainWorldData()`/`CopyDowned()` subsequently captures is already correct -- so the later, unconditional `ReadCopiedMainWorldData()`/`ReadCopiedDowned()` re-application (which fires right after the main world's real file is correctly reloaded) becomes a no-op instead of a corruption. Verified base-class method signatures (`public virtual void OnEnter()` / `public virtual void OnExit()`, namespace `SubworldLibrary`, class `Subworld`) via a live fetch of `Subworld.cs` before writing the overrides, rather than guessing.
  This does not touch or attempt to patch SubworldLibrary itself (no editable local source, and the underlying behavior is confirmed-intentional upstream, not a bug) -- it neutralizes the leak from BossArenaSubWorld's own subworld class instead, which is the correct layer for a consuming mod to defend at.
  Scope note (informational, not changed by this fix): the fix only guards the vanilla whitelist `CopyDowned()` covers. It does not and cannot address WorldGen side effects (ore conversion, etc., which never touch the main world's real tiles regardless) or modded boss flags (Calamity/Spirit/etc., which were never affected by this specific mechanism to begin with and still require the carrier-item architecture, unchanged from PROJECT.md's original design).
